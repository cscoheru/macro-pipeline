## 1. Problem Statement

用户希望把李厚辰的 YouTube 频道“世界苦茶” `@flipradio_fearnation` 变成一个可持续更新、可检索、可追溯、能观察思想演变的个人研究库，而不是一次性总结若干视频。

当前事实：

- 频道公开页约有 637 条视频，手工逐条下载、转录和阅读不可持续。
- 仓库中已有两篇语音转文字 DOCX，可用于术语、文风和分析模板校准，但它们未必具有可靠的 YouTube 视频 ID 与逐句时间戳。
- 抽样检查显示，至少部分频道视频已经存在创作者字幕或 YouTube 自动字幕。因此首选“字幕优先”，而不是下载音视频后统一跑语音识别。
- 用户最关心的是人物思想地图；与现有宏观数据库联动是第二目标，不能反过来扭曲人物研究。

目标不是“让模型写一篇李厚辰思想综述”，而是建立以下可审计对象：视频、带时间戳文本、概念、原子主张、论证关系、证据提及、预测、思想变化和外部评价。

## 2. What Makes This Cool

最有价值的最终形态是一个有时间轴的“认识论数字孪生”：研究者可以回到任意日期，看到李厚辰当时使用哪些概念、持有哪些主张、依赖哪些论证、哪些预测后来得到支持或被挑战，以及他的概念含义如何漂移。

第一版不追求宏大展示，而要先做到一件少见但基础的事：任何系统生成的结论，都能一键回到原视频的准确时间点；任何无法追溯的模型判断，都不能混进“李厚辰说过什么”。

## 3. Goals and Non-goals

### 3.1 Goals

1. 全量编目频道公开视频元数据，并支持重复运行、断点续跑和状态审计。
2. 对有中文字幕的视频抓取一份且仅一份“首次成功字幕原件”，之后永不覆盖。
3. 把字幕确定性地规范化为带时间戳的片段，同时保留到原始字幕的映射。
4. 在 8–12 个近期分析类视频上跑通完整垂直切片：字幕 → 原子主张 → 概念 → 论证关系 → 校验 → Obsidian 页面。
5. 严格分离三层内容：
   - `speaker_statement`：李厚辰实际表达的内容；
   - `speaker_reasoning`：他在节目中给出的推理、因果链和证据提及；
   - `system_evaluation`：模型、用户或宏观资料对上述内容的评价。
6. 形成稳定领域骨架，同时允许语料中涌现的新概念先进入候选区。
7. 为未来与宏观数据建立只读桥接接口，但第一实施阶段不得写入或迁移现有宏观数据库。

### 3.2 NOT in scope (explicitly deferred)

以下内容不属于首个可验收版本：

- 不下载或永久保存频道全部音视频。
- 不为缺字幕的全部视频立即运行 Whisper。
- 不使用向量数据库、图数据库或 Graphiti 作为首版依赖。
- 不自动判定李厚辰“自相矛盾”“预测正确”或“预测错误”。
- 不自动把模型提出的新概念提升为正式概念。
- 不做模型微调，不开发独立 Web UI。
- 不公开转载完整字幕；研究库默认是本地个人用途。
- 不修改现有宏观流水线的表、状态机、定时任务和发布路径。

## 4. Constraints and Locked Premises

以下前提已经由用户确认，Claude Code 不得自行改写：

1. **字幕优先**：优先提取已有中文字幕；只有覆盖率报告证明缺口值得处理，并获得用户另行授权后，才设计 ASR 阶段。
2. **原始字幕单快照永久冻结**：每个视频只保留第一次成功取得且符合选择规则的字幕原件。数据库和文件均不得覆盖、修订或删除。上游字幕将来发生修订也忽略。这是用户明确选择，不改成“多版本原始字幕”。
3. **派生物可版本化**：清洗算法、分段、模型输出、人工修订和页面渲染都必须有版本，可重新生成，不能回写原始字幕。
4. **可追溯是硬门禁**：每个正式概念定义、主张和论证边必须追溯到 `video_id + transcript_version + segment range + timestamp URL + exact quote`。缺任一项则不能进入正式层。
5. **三层分离**：系统评价不得伪装为说话者陈述；外部资料不得伪装成节目中的证据。
6. **分阶段分析**：先完成全量元数据与字幕覆盖审计，再对小样本做高质量分析；不允许一次调用模型分析 600 多条视频。
7. **独立命名空间**：研究库使用独立数据库、产物根目录和 Obsidian 路径；运行本项目不得改变现有宏观记录。
8. **执行职责**：Claude Code 实现；Codex 只做验收和文档补充，不替 Claude Code 修一行实现代码。

## 5. Source Strategy

### 5.1 Authoritative acquisition path

首选 [yt-dlp 官方项目](https://github.com/yt-dlp/yt-dlp) 完成频道编目、视频信息和字幕发现/获取。调用必须使用参数数组，禁止对视频标题、频道标题或视频 ID 做 shell 拼接，禁止 `shell=True`。

建议的逻辑步骤，而非必须逐字照搬的命令：

1. 用频道根 URL 做 metadata-only 编目，并明确覆盖常规视频、直播/回放和 Shorts；若 yt-dlp 当前版本不能从根 URL 稳定覆盖全部 tab，则分别枚举 `/videos`、`/streams`、`/shorts` 后按 `video_id` 去重。不得下载媒体。
2. 对每个视频独立检查字幕清单。
3. 按第 5.2 节规则选择一个中文字幕轨道。
4. 用 metadata-only / subtitles-only 方式取得字幕和 info JSON。
5. 先以临时文件写入，计算 SHA-256，事务性登记后原子移动到内容寻址路径。

工具版本需记入每次运行和每份原始字幕记录。预检要给出可操作错误：未安装、版本过旧、YouTube 提取器失败、网络失败、视频不可用、需要登录、没有字幕，不能都归为同一个 `download_failed`。

编目运行只有在所有计划 tab 都成功枚举时才可标为 `success`；部分 tab 失败应标为 `partial`，保留已经取得的条目并记录缺口。频道公开总数只用于对账，不作为数据库主键或绝对真值。数据库需记录条目来自哪个 tab/collection，以便解释重复、缺失和 yt-dlp 行为变化。

### 5.2 Frozen subtitle selection

每个视频最多冻结一个中文轨道，选择规则必须确定且有单元测试：

1. 人工字幕优先于自动字幕；
2. 语言优先序写入配置，建议初始值：`zh-Hans`, `zh-CN`, `zh`, `zh-Hant`, `zh-TW`；
3. 同等条件下选择能保留毫秒时间戳和文本的结构化格式，首选 `json3`，其次 `vtt`；
4. 只有完整下载、格式解析成功、至少一个非空 cue、SHA-256 计算成功后，才称为“首次成功”；
5. 一旦 `raw_caption` 记录存在，后续运行必须返回 `already_frozen`，不得再次访问字幕下载端点以尝试替换；
6. 第一次失败不冻结，允许按退避策略重试；
7. 如果先冻结了自动字幕，之后出现人工字幕，仍然忽略，并在已知限制中显示。

若一次运行内高优先轨道下载/最小语法校验失败，可以继续尝试下一个候选；第一个按优先序完整下载、能解析出至少一个非空 cue 且哈希成功的候选即为“首次成功”。一旦数据库插入获胜，任何并发或后续候选都必须停止且无副作用。

[youtube-transcript-api](https://github.com/jdepoix/youtube-transcript-api) 依赖未公开接口且官方 README 明确提示 IP 封禁/失效风险，因此首版不得把它作为主路径。若未来加入，只能作为默认关闭、可观测、可移除的 fallback。

### 5.3 ASR fallback

[faster-whisper](https://github.com/SYSTRAN/faster-whisper) 仅列为未来候选。首版不得下载模型、媒体或增加 GPU 依赖。启用 ASR 前必须先提交：缺字幕比例、缺失视频价值抽样、预计存储/计算成本、媒体保留策略和单独验收标准。

## 6. Isolation and Storage Layout

建议默认布局：

```text
data/houchen/
  houchen.sqlite3
  raw/
    captions/<sha256-prefix>/<sha256>.<ext>
    metadata/<sha256-prefix>/<sha256>.json
  derived/
    transcripts/<normalizer-version>/<sha256>.json
  artifacts/
    analysis/<analysis-run-id>.json
    markdown/<content-sha256>.md
  failures/
    <run-id>/<video-id>.json
```

要求：

- 禁止复用现有宏观数据库文件作为研究库数据库。
- 所有路径通过一个明确的配置入口解析；测试必须能把根目录指到临时目录。
- 内容寻址文件写入采用 temp → fsync/close → atomic rename；数据库只登记已经完整落盘的 SHA。
- 日志不得包含 API key、cookie、完整模型响应或用户主目录中的其他秘密路径。
- 如果 Obsidian 发布启用，使用独立前缀，例如 `Research/世界苦茶/`，不得进入现有宏观文章目录。

## 7. Data Model

使用独立 SQLite 数据库和显式关系模型。名称可依项目风格微调，但语义、约束与分层不能丢失。

### 7.1 Corpus and provenance tables

#### `schema_version`

追加式迁移记录。沿用现有 `lib/migrations.py` 的理念，但研究库有自己的迁移入口和版本序列。

#### `corpus_run`

- `run_id`，主键；
- `kind`：`catalog | caption_fetch | normalize | analyze | validate | publish | macro_link`；
- `started_at`, `finished_at`, `status`；
- `config_sha256`, `tool_versions_json`, `summary_json`；
- 失败时保存结构化错误类别和可重试标记。

#### `video`

- `video_id`，YouTube ID 主键，须通过格式校验；
- `channel_id`, `channel_handle`, `canonical_url`；
- `title`, `description`, `published_at`, `duration_sec`；
- `live_status`, `availability`, `content_kind`；
- `discovered_at`, `last_seen_at`, `metadata_sha256`；
- 不把标题用作标识符或路径。

元数据允许刷新；每次刷新要更新 `last_seen_at` 并保留最新 metadata 原件的 SHA。若决定保留元数据历史，应另建追加表，不能妨碍字幕单快照规则。

#### `raw_caption`

- `video_id` 唯一且外键指向 `video`；
- `language`, `caption_kind` (`manual | auto`), `format`；
- `content_sha256`, `local_path`, `byte_count`, `cue_count`；
- `fetched_at`, `yt_dlp_version`, `source_metadata_sha256`；
- 数据库触发器拒绝 `UPDATE` 和 `DELETE`；
- 插入冲突必须是无副作用的 `already_frozen`，不能覆盖。

#### `transcript_version`

- `transcript_version_id`；
- `video_id`, `raw_caption_sha256`, `normalizer_name`, `normalizer_version`；
- `created_at`, `content_sha256`, `status`；
- 对同一输入与同一规范化版本设置唯一约束，保证幂等。

#### `transcript_segment`

- `transcript_version_id`, `ordinal` 联合唯一；
- `start_ms`, `end_ms`, `text`；
- `raw_cue_start`, `raw_cue_end` 或等效反向映射；
- `speaker` 可空；未可靠分辨说话者时不得默认填“李厚辰”。

### 7.2 Intellectual model tables

#### `domain`

首版稳定领域骨架，使用固定 slug；名称可人工修订但 slug 稳定。建议初始集合：

- `political_economy`：政治经济与分配；
- `state_governance`：国家、央地关系与治理；
- `society_psychology`：社会结构、群体心理与行动；
- `international_order`：国际秩序与地缘政治；
- `technology_ai`：技术、平台与人工智能；
- `history_interpretation`：历史解释；
- `method_media`：方法论、知识生产与媒体。

骨架是导航，不强迫每个概念只属于一个领域。

#### `concept`

- `concept_id`, `canonical_name`, `definition`；
- `status`：`proposed | canonical | deprecated`；
- `origin`：`seed | corpus | human`；
- `first_seen_at`, `last_seen_at`；
- 自动发现的新概念只能进入 `proposed`。

#### `concept_alias` / `concept_domain`

处理同义词、别称和多领域归属。别名合并必须可逆并记录操作者和时间。

#### `concept_source`

语料中形成的 canonical concept definition 必须至少一条来源，字段与 `claim_source` 等价：视频、transcript version、片段范围、时间戳、逐字引文和 raw caption SHA。`seed` 仅可作为导航骨架或候选定义；没有语料来源时不得显示为“李厚辰对该概念的定义”。

#### `claim`

一条记录只表达一个可独立引用的原子主张：

- `claim_id`, `video_id`, `claim_text`；
- `claim_type`：`definition | descriptive | causal | predictive | normative | interpretive`；
- `speaker`, `layer`，正式说话者主张只能是 `speaker_statement`；
- `temporal_scope`, `modality`, `status`；
- `analysis_run_id`, `created_at`；
- 不保存无法定位来源的“频道总体观点”作为正式 claim。

#### `claim_source`

每个正式 claim 至少一条来源：

- `claim_id`, `transcript_version_id`；
- `segment_start_ordinal`, `segment_end_ordinal`；
- `start_ms`, `end_ms`, `exact_quote`, `timestamp_url`；
- `raw_caption_sha256`；
- 校验器必须证明引文在所指片段按允许的空白归一规则后精确匹配。

#### `claim_concept`

主张与正式或候选概念的多对多关系，记录 `relation` 和来源分析运行。

#### `reasoning_edge`

- `from_claim_id`, `to_claim_id`；
- `relation`：`supports | causes | qualifies | contradicts | predicts | defines | exemplifies`；
- `layer`：`speaker_reasoning | system_evaluation`；
- `source_id`：说话者论证边必须有逐字引文与时间戳；系统推断边必须单独标注分析运行，不能冒充说话者推理。

#### `evidence_mention`

记录节目中“他提到了什么证据”，不是记录证据已被系统核实。至少包括原文、时间戳、提及类型和可空的外部实体候选。

#### `external_evidence`

未来评价所用外部材料，至少记录来源 URL/本地数据键、发布者、观察期、抓取时间、内容哈希和证据等级。不得只保存模型摘要。

#### `evaluation`

- 明确指向一个 claim 或 reasoning edge；
- `evaluator`：`human | model | macro_bridge`；
- `as_of`, `verdict`, `reasoning`, `status`；
- `macro_bridge` 评价没有 `external_evidence` 时不得成为正式评价；
- 评价页面与“李厚辰说了什么”页面在视觉与字段上明确分离。

#### `forecast`

仅收录可判定、有时间范围或结果条件的预测性主张。状态变化必须有证据和人工确认；模型只能提出 `candidate`，不能自行判定命中或失败。

## 8. Transcript Normalization

规范化必须是纯函数式、确定性、可版本化的派生步骤：

1. 解析 `json3`/`vtt` cue，保留毫秒时间戳；
2. 去除纯格式标记、空 cue 和确定性的滚动字幕重复；
3. 合并规则必须有上限，不能把跨主题长段合成一个片段；
4. 中文标点补全若使用模型，必须作为另一个派生版本，不能冒充确定性规范化；首版建议不依赖模型补标点；
5. 所有规范化片段保留到原 cue 范围的映射；
6. 引文展示来自被冻结的字幕文字，允许的匹配归一仅限 Unicode 规范化和连续空白折叠；不能用模型润色后的文字作为 `exact_quote`；
7. 重跑相同版本得到完全相同的 JSON、SHA-256 和数据库行。

## 9. Analysis Contract

### 9.1 Input bundle

每次模型分析输入是内容寻址的 `analysis_input`，至少包括：

- 视频 ID、标题、日期、系列/类型候选；
- transcript version 与 segment 列表；
- 当前领域骨架与 canonical concepts；
- 明确的三层定义和禁止事项；
- prompt version、schema version、模型/provider 标识。

### 9.2 Structured output

模型输出必须通过 JSON Schema，并且不得直接写正式表。先进入候选产物，再由硬校验器转换。输出至少包含：

- atomic claim candidates；
- 每个 claim 的类型、说话者、片段范围、逐字引文；
- concept links 与 proposed concepts；
- speaker reasoning edges 及其独立来源片段；
- evidence mentions；
- forecast candidates；
- 不确定项和拒绝抽取的原因。

### 9.3 Hard validator

以下任一情况必须进入 `needs_review` 或被逐项拒绝，不能发布为正式数据：

- 缺视频 ID、transcript version、片段范围、时间戳 URL 或逐字引文；
- 引文无法在所指字幕片段中匹配；
- 片段范围越界或时间倒序；
- 未知说话者被强行归因给李厚辰；
- 一条 claim 包含多个可拆分判断；
- 把模型的总结或外部事实写成 `speaker_statement`；
- `speaker_reasoning` 边没有节目内来源；
- 外部评价没有来源哈希和观察期；
- proposed concept 被自动升级；
- 预测没有可判定内容，只是一般性态度。

校验输出必须包含逐项拒绝报告，便于修改 prompt 或人工复核；不能只返回 `invalid`。

## 10. Search and Navigation

首版使用 SQLite FTS5，参考 [SQLite FTS5 官方文档](https://sqlite.org/fts5.html)。至少为规范化字幕、正式主张、概念名称/别名建立全文检索。

首版不引入 embedding。只有在固定查询集上证明 FTS5 无法满足中文检索需求，且给出召回/成本对比后，才提交向量检索提案。

至少支持以下研究问题：

- 某概念在哪些视频首次/集中出现？
- 一条主张的原视频、时间点和精确引文是什么？
- 某时间段内，预测性主张有哪些？
- 同一概念在不同时段的定义或关联主张如何变化？
- 哪些内容是系统评价，而不是李厚辰的原话？

## 11. Obsidian Output

复用现有 `VaultWriter` 和“PUT → GET 读回 → SHA-256 核验”的发布模式，但使用研究库独立发布记录和路径。

建议输出：

```text
Research/世界苦茶/
  README.md
  Videos/<YYYY>/<video-id>.md
  Concepts/<concept-slug>.md
  Claims/<claim-id>.md             # 可按规模决定是否单页
  Forecasts/index.md
  Reviews/needs-review.md
  Reports/caption-coverage.md
```

页面要求：

- 每个视频页包含 YouTube 链接、日期、字幕类型、分析版本和主张列表；
- 每条主张显示准确时间链接和短引文；
- 概念页按时间排序，区分 canonical definition、说话者使用和系统分析；
- 页面顶部标出“机器提取 / 已校验 / 人工复核”状态；
- 模型评价使用独立 callout/章节，不能与原话混排；
- 同一输入与同一渲染版本重复发布，文件字节和 SHA 不变；
- 公开发布不是本任务目标，页面不得嵌入完整原始字幕。

## 12. Macro-data Bridge (Secondary Goal)

这一阶段只设计接口，不允许写现有宏观库。

1. 研究库内可建立 `macro_link_candidate`，记录 claim、宏观 observation key、关系类型、时间窗、生成者和状态。
2. 读取现有宏观数据时使用 SQLite read-only URI 或现有只读查询 API；不得调用 `upsert_observations`、迁移或状态变更函数。
3. 关系类型建议：`supports | challenges | contextualizes | unresolved`，全部先是 candidate。
4. 正式宏观评价必须保存外部 observation 的来源、指标、单位、观察期、发布时间和读取时数据哈希。
5. 首个实施 PR 只需保留稳定接口或导出 JSONL；真正自动联动放到单独 PR，并再次验收。

## 13. State Machine and Idempotency

建议视频处理状态：

```text
discovered
  -> caption_pending
  -> caption_frozen | caption_missing | unavailable | retryable_error
caption_frozen
  -> normalized
  -> analysis_pending
  -> candidates_ready
  -> validated | needs_review
validated
  -> rendered
  -> published
```

要求：

- 网络类错误与永久类错误分开；只有可重试错误进入退避重试。
- 每次状态转换记录 actor、时间和理由；不能靠覆盖一列丢失历史。
- 中断后从最后一个持久化边界继续；不得重复调用模型或重复写 raw caption。
- 输入哈希 + prompt/schema/model version 决定 analysis run identity；相同 identity 默认 no-op。
- 新模型/新 prompt 产生新 analysis run，旧结果保留，可比较，不原地覆盖。

原始文件读取时应重算或抽样核验已登记 SHA；发现内容不匹配应停止派生处理并报告 `raw_integrity_error`，不能悄悄按被篡改的字节继续生成。

## 14. CLI Contract

建议提供一个单一入口，例如 `scripts/houchen_pipeline.py`。命令名可调整，但能力和机器可读输出必须存在：

```text
preflight
catalog [--channel URL] [--limit N]
fetch-captions [--video-id ID | --pending] [--limit N]
normalize [--video-id ID | --pending]
analyze [--video-id ID | --sample N]
validate [--analysis-run ID | --pending]
publish [--video-id ID | --validated]
status [--json]
coverage [--json | --markdown]
```

通用要求：

- 支持 `--dry-run` 的命令不得写数据库、文件或 Vault；
- 支持明确的 `--data-root` 或测试配置；
- `status --json` 和 `coverage --json` 输出有版本字段，便于验收；
- 退出码区分成功、部分成功、配置错误和运行失败；
- 默认命令不做全频道模型调用；批处理必须要求显式 limit 或显式确认标志；
- 所有外部进程有 timeout、捕获 stderr，并把可展示错误做长度限制。

## 15. Security and Robustness Requirements

因为实现会处理外部 API/网页数据和模型输出，至少覆盖 OWASP 风险中的注入、XSS/内容注入、认证/秘密泄漏：

- subprocess 始终传 argv，不拼 shell；视频 ID、语言码和路径组件使用 allowlist；
- YouTube 标题/描述、字幕和模型输出一律视为不可信文本，不允许控制命令、路径或 prompt 的系统指令；
- Markdown 渲染转义/拒绝 raw HTML、`javascript:` 链接、嵌入图片和任意文件链接；
- 发布路径由内部 ID 生成，不能由标题直接生成；
- API key/cookie 只从受控 env 文件或环境变量读取，不进入数据库、artifact、日志和异常消息；
- 首版不得自动读取浏览器 cookie；如视频需要认证，只记录 `auth_required`；
- 设置下载大小、字幕 cue 数、单视频时长、模型输入长度和响应长度上限；
- SQLite 外键开启，事务边界清楚，忙等待和并发锁错误可诊断；
- 所有时间使用 UTC 存储，展示层再转时区。

## 15.1 Performance and resource bounds

- 频道条目、字幕任务和数据库写入采用有界批次；不得一次把所有字幕正文或全频道模型输入装入内存。
- catalog 可接受一次 flat JSON，但解析层须对异常大输出设置字节上限；若使用 JSONL，应流式处理。
- caption/analyze worker 首版默认并发为 1；并发提升必须显式配置，并受全局上限、退避和 SQLite busy timeout 约束。
- 每个视频在独立事务边界提交，避免一个失败回滚整批，也避免 600 多条长事务持锁。
- 为 `video.availability`、任务状态、`transcript_segment(transcript_version_id, ordinal)`、`claim.video_id`、来源外键和时间查询建立必要索引；用固定查询集检查查询计划。
- coverage/status 使用 SQL 聚合，不逐视频 N+1 查询。
- 模型输入按片段有界切块，跨块主张合并必须保留各自来源；切块策略属于 PR-3 并需 eval。

## 17. Test Plan

### 17.1 Required fixture tests

测试夹具不得依赖实时 YouTube：

- flat playlist metadata：正常视频、直播回放、Short、已删除/私密条目、重复条目；
- subtitle inventory：人工简中、人工繁中、自动中文、无字幕、多轨道；
- json3/vtt：滚动重复、空 cue、重叠时间、HTML/格式标签、超长 cue、非 BMP 字符；
- provider outputs：合法、缺来源、引文不匹配、越界、混层、多原子 claim、未知概念、prompt injection 文本；
- VaultWriter：成功、PUT 后 GET 不一致、网络失败、重复发布。

### 17.2 Required invariants

1. **Frozen raw**：第一次成功插入后，第二次、并发两次和换字幕轨道三种情况都不能修改 SHA、文件 mtime 或记录。
2. **Crash safety**：模拟“文件写完数据库未提交”和“数据库准备中进程退出”，恢复后没有半条正式记录或损坏文件。
3. **Idempotency**：相同输入、相同版本重跑，数据库净新增为 0，派生物 SHA 不变。
4. **Provenance**：任意正式 claim 可从数据库反查到视频、字幕 SHA、片段和时间 URL；抽查 URL 秒数等于 `start_ms // 1000`。
5. **Quote integrity**：正式 quote 100% 通过精确匹配；故意篡改一个字即失败。
6. **Layer isolation**：inference/evaluation fixture 不会落入 speaker statement；未知 speaker 不默认归因。
7. **Version isolation**：改 prompt 或 normalizer version 产生新派生版本，旧版本仍可读取。
8. **Macro isolation**：所有 PR-1 至 PR-4 测试和 smoke run 不打开宏观库写连接；现有宏观表不变化。
9. **Safe rendering**：字幕中的 HTML、Markdown 图片、危险链接和路径穿越字符串不能进入可执行/可加载形式。
10. **Stable publishing**：同一 validated artifact 重发为 no-op；读回 hash 不同则保持未发布并报错。

### 17.3 Live smoke tests

网络 smoke 与默认测试分离，必须显式运行。使用 1–3 个公开视频验证：

- 能看到频道条目；
- 能列出字幕；
- 能冻结一个中文轨道；
- 立即重跑得到 `already_frozen`；
- 不产生音视频文件。

不要在 CI 或验收中默认编目/分析 637 条，也不要让测试消耗真实模型额度。

## 18. Acceptance Criteria

整个 MVP 视为完成，必须同时满足：

- PR-1 至 PR-4 的阶段测试全部通过，且每个阶段有可复现命令；
- 频道编目覆盖报告说明：发现总数、公开视频、不可用、Short、直播、人工字幕、自动字幕和无中文字幕数量；总数与当时频道公开数量差异有解释；
- 每个已冻结视频只有一条 raw caption，数据库触发器和文件策略共同防覆盖；
- 8–12 个分析类视频跑通，产出 20–30 条正式原子主张和 4–6 个有内容的概念页；
- 正式主张来源完整率和 exact-quote 通过率均为 100%；
- 随机抽查至少 10 条时间链接，视频和语义位置正确；
- `speaker_statement`、`speaker_reasoning`、`system_evaluation` 可用数据库查询和页面样式明确区分；
- 失败记录能按错误类别统计，并可安全重试；
- 运行前后现有宏观数据和现有发布产物无变化；
- 没有 `.mp3`、`.m4a`、`.webm`、`.mp4` 等媒体文件被首版流程持久化；
- README/运维文档说明首次运行、增量更新、备份、恢复、工具升级和已知限制；
- Claude Code 提供改动清单、测试输出和未完成项，不执行 commit/push。

## 19. Known Limitations Accepted by the User

1. 单快照冻结意味着上游字幕错误即使后来修正，本地 raw caption 也不会同步；只能用新的派生修订/人工注释纠错。
2. 自动字幕可能存在错字、断句和说话者混淆；系统必须用“不确定”而不是猜测来处理。
3. 无字幕视频在首版只被编目，不会获得内容分析。
4. 频道删除、私密化或地区限制可能使总数与公开页计数不一致。
5. YouTube 和 yt-dlp 的提取行为会变化；live smoke 失败不应自动解释为代码逻辑错误。
6. 两个 DOCX 若无法映射到视频和时间戳，只能用于校准，不能进入正式可追溯语料层。
7. 首版的“思想变化”是按时间浏览和对比主张，不是模型自动宣布立场改变。

## 20. Failure Modes and Recovery

| Failure | Required behavior | Recovery |
|---|---|---|
| yt-dlp 未安装/过旧 | preflight 明确失败，不写业务状态 | 用户升级后重跑 |
| 视频私密/删除/地区限制 | 记录 availability，不无限重试 | 后续 catalog 刷新 |
| 无中文字幕 | 标为 caption_missing | 覆盖报告后决定 ASR |
| 下载中断/空文件 | 不创建 frozen 记录 | 清理临时文件后退避重试 |
| 并发冻结同一视频 | 一个事务成功，另一个无副作用 | 返回 already_frozen |
| 字幕最小语法/非空校验失败 | 不冻结该候选，可尝试下一个语言轨道 | 修复下载/格式支持后重试 |
| 完整规范化失败 | raw 已冻结且保持不变，derived 状态记录失败 | 修复 normalizer 后生成新 derived version |
| 模型超时/限流 | 保留 input artifact，标 retryable | 不重复已成功的步骤 |
| 模型输出不合规 | needs_review + 逐项错误 | 调 prompt/version 后新 run |
| 发布 PUT 成功但读回不一致 | 不标 published | 重试或人工检查 Vault |
| SQLite 损坏/磁盘满 | 停止写入，保留原始内容寻址文件 | 从备份恢复后重新索引 |

冻结策略已固定：下载格式通过最小语法解析并含至少一个非空 cue 后即冻结 raw；去重、合并、标点和完整规范化全部属于 derived 阶段。Claude Code 不再把这一点视为开放产品决策。

## 21. Observability and Operations

`status --json` 至少返回：

- schema/output version；
- catalog 总数及 availability 分布；
- caption pending/frozen/missing/retryable/permanent error；
- normalized/candidate/validated/needs_review/published；
- 最老待处理项；
- 最近错误按类别计数；
- 当前工具、normalizer、prompt、schema 和 renderer 版本。

运行日志使用结构化事件或一致字段，至少有 `run_id`, `video_id`, `stage`, `outcome`, `error_class`, `retryable`, `duration_ms`。原始字幕内容和完整模型响应不进普通日志。

备份至少覆盖独立 SQLite、raw 内容寻址目录和人工修订。派生文件可重建，但保留它们有助于审计。

## 28. Cross-model Perspective

独立冷读认为，长期最有价值的版本是能按日期重建人物世界观的 temporal epistemic twin，包括概念漂移、预测台账和反事实简报。但首个有用原型应非常克制：先以两份 DOCX 校准，再选 8–12 个近期分析视频，抽取 4–6 个概念与 20–30 条原子主张，做出一张真正好用的 Obsidian 概念页。

冷读特别强调的门禁包括：重复导入幂等、来源必填、引文和时间戳匹配、推断不得存成说话者证言、宏观评价必须有外部证据、版本可区分、现有宏观记录零影响和 Obsidian 稳定重生成。它建议首版跳过全量深度分析、Whisper、向量库、本体自动生长、自动矛盾裁决、微调和自定义 UI。本任务书采纳这些收缩建议；但按照用户选择，没有采纳“原始字幕多快照版本化”。

## 29. Approaches Considered

### Approach A: 独立 SQLite 显式思想模型（选定）

用关系表明确表示主张、来源、概念、论证和评价，以内容寻址 artifact 保留模型输入输出，以 FTS5 提供检索。优势是可审计、适合分阶段、容易与现有 Python/SQLite 模式衔接，并为未来图分析保留明确边。

### Approach B: 文件优先的 JSONL / Markdown MVP

实现更快，但来源约束、幂等、跨视频关系和状态审计会迅速依赖约定，后期迁移成本高。可作为导出格式，不作为事实底座。

### Approach C: 直接使用 temporal knowledge graph

概念漂移和时间查询很诱人，[Graphiti](https://github.com/getzep/graphiti) 等项目可作为未来模式参考，但首版引入图数据库、图抽取和双存储一致性会扩大故障面。当前不采用。

## 30. Recommended Approach

采用 Approach A，但按 PR-1 至 PR-4 逐步交付。关系库先把证据链和分层做对；`claim` 与 `reasoning_edge` 天然可以在未来投影成图，无需现在承担图数据库运维。全量工作只用于元数据和字幕覆盖，模型深度分析先限制在 8–12 个视频。这样最早能得到真实研究价值，同时保住之后扩展到 637 条视频、宏观联动和时间演化分析的路径。
